# 선택형 워크플로의 단일 Elicitation 진입점

## 상태

채택

## 결정

- 사용자 선택이 필요한 `init_work`, `resume_work`, `scan_pdf`, `prepare_ocr`,
  `set_chapters`, `finalize_study`, `cleanup_work`는 각각 등록된 async MCP 함수
  하나로만 구현한다.
- 각 함수는 Elicitation capability 확인, form 요청, 응답 검증, 승인 후 실행을
  같은 호출 안에서 처리한다.
- 같은 작업을 선택 인자로 직접 실행하는 별도 동기 함수, `_{tool}_impl` 함수,
  별도 MCP wrapper를 두지 않는다.
- 공개 스키마는 사용자 선택 인자를 받지 않으며, Elicitation 미지원·거절·취소
  시 승인 뒤 처리와 상태 변경을 실행하지 않는다.
- 회귀 테스트는 일곱 함수가 async이고 `ctx`를 요구하는지, 대응하는
  `_{tool}_impl` 속성이 없는지, MCP 공개 스키마에 선택 인자가 없는지를 함께
  검사한다.

## 이유

Elicitation wrapper와 선택값을 받는 별도 실행 함수가 함께 있으면, 서버 코드를
확인할 수 있는 에이전트가 wrapper 대신 실행 함수를 선택해 사용자의 결정을 우회할
수 있다. 선택 요청과 실행을 하나의 등록 함수로 결합하면 동일 워크플로의 공식
Python 진입점이 둘로 갈라지지 않는다.

## 한계

이 결정은 MCP 도구와 동일한 전체 워크플로의 직접 호출 우회를 제거한다. 동일 OS
사용자에게 임의 Python·셸 실행과 결과 폴더 쓰기 권한까지 제공한 상태를 보안
샌드박스로 만들지는 않는다. 그 권한까지 격리해야 하면 MCP 서버와 결과 폴더를
별도 OS 사용자 또는 샌드박스에 두고 에이전트에는 MCP 전송만 허용해야 한다.
