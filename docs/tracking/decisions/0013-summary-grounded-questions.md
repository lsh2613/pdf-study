# 모든 문제는 검토된 요약을 근거로 생성

## 배경

기존 생성기는 챕터 원문 전체를 요약과 기본 문제 생성에 함께 사용했고, 확장 문제
생성기에도 같은 원문을 전달했다. 이 구조에서는 요약에서 의도적으로 생략된 세부
정보가 문제, 보기, 정답이나 해설에 다시 나타날 수 있다. 그러면 학습자가 먼저 읽은
요약만으로 문제를 풀 수 있다는 보장이 약해진다.

## 결정

- 원문 text와 section inventory는 요약 생성과 의미 보존 검토까지만 사용한다.
- 검토를 통과한 뒤 별도 기본 문제 생성 단계에는 `summary`, `key_points`와 문제
  개수 상한 계산용 `source_char_count`만 전달한다.
- 확장 문제도 `get_chapter_summary`가 반환한 동일한 요약 입력만 사용한다.
- `get_chapter_summary`는 원문 text, section inventory, summary review 내부 정보를
  반환하지 않는다.
- `source_char_count`는 문제 개수 상한을 고르는 메타일 뿐 문제 내용의 근거가
  아니다.
- 기존 `summarizer_prompt` 응답 키는 호환을 위해 유지하되, 새 workflow는
  `summary_prompt`와 `basic_question_prompt`를 분리해 사용한다.

## 대안

- 한 프롬프트에 원문과 요약을 함께 주고 요약만 참조하라고 지시: 모델이 이미 본
  원문의 세부 정보를 문제에 섞을 수 있다.
- 문제 개수 상한도 요약 글자 수로 변경: 같은 원문의 요약 표현이나 길이에 따라 문제
  수가 불필요하게 흔들리고 기존 저장 계약과 호환되지 않는다.
- 저장 API에서 문제의 의미를 자동 판정: 문자열 계약 검증만으로는 각 문제의 모든
  사실이 요약에 근거하는지 신뢰성 있게 판정할 수 없다.

## 결과

새 생성 workflow의 모든 기본·확장 문제는 학습자가 보는 저장 요약만으로 답하거나
사고를 확장할 수 있다. 확장 문제만 재개할 때는 raw 본문이 없어도 저장 요약이
정상이면 계속 진행할 수 있다. 저장 payload와 렌더러의 문제 스키마는 바뀌지 않는다.
