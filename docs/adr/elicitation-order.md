# Elicitation 순서 보장 결정

## 상태

채택 — 2026-08-03

## 배경

`init_work`에서 단답형·주관식·확장형 선택을 하나의 다중 필드 MCP form으로
요청했을 때, 서버의 JSON Schema 속성 선언 순서와 Codex 클라이언트의 실제 탐색
순서가 일치하지 않았다. 속성을 정상 순서와 역순으로 바꾸는 방식은 실행 중인 MCP
프로세스의 이전 코드와 클라이언트 렌더링 동작이 섞여 진단을 어렵게 했고, 특정
클라이언트 동작에 의존하므로 재발 가능성이 있었다.

stdio MCP 서버는 Python 소스 변경을 자동으로 다시 읽지 않는다. 따라서 서버 파일을
수정해도 이미 실행 중인 프로세스에서는 이전 form이 계속 표시될 수 있다.

## 결정

- 사용자에게 묻는 순서가 외부 계약인 선택은 하나의 다중 필드 form에 넣지 않는다.
- 문제 유형은 각각 단일 필드 form으로 다음 순서대로 `ctx.elicit`을 호출한다.

  1. 단답형 문제 생성
  2. 주관식 문제 생성
  3. 확장 문제 생성

- 세 유형 중 하나라도 포함한 경우에만 학습자 정보 form을 네 번째로 연다. 모두
  제외하면 학습자 정보를 묻지 않고 빈 값으로 확정한다.
- 각 문제 유형 form의 `message`에는 해당 유형의 설명이나 질문만 넣고, 필드
  `title`에는 짧은 한국어 항목명을 넣는다.
- 앞선 form의 응답은 메모리에만 보관한다. 필요한 form이 모두 승인되기 전에는 작업
  생성, PDF 스캔 또는 `.work/state.json` 변경을 시작하지 않는다.
- JSON Schema 속성 순서를 뒤집거나 필드명·`required` 배열 순서에 의존해 화면 순서를
  맞추는 보정 코드는 추가하지 않는다.

## 검증 규칙

- 테스트는 단순히 한 form의 속성 순서를 검사하지 않고, 실제 Elicitation 호출이
  `단답형 → 주관식 → 확장형` 순서로 발생하는지 검사한다.
- 하나 이상 포함한 경우 호출 순서는 `단답형 → 주관식 → 확장형 → 학습자 정보`여야
  하며, 모두 제외한 경우 호출 수는 세 번이어야 한다.
- FastMCP client/server 왕복 테스트에서도 각 문제 유형의 `requestedSchema`가 단일
  속성만 가지는지 확인한다.
- MCP form 코드를 수정한 뒤 수동 확인할 때는 서버를 재연결하거나 새 Codex 세션을
  시작한다. 계속 이전 화면이 보이면 다음을 확인한다.

  - MCP 설정의 Python 실행 경로와 `-m pdf_learner` 인자
  - 실행 디렉터리에서 `pdf_learner.server.__file__`이 가리키는 파일
  - MCP 프로세스 시작 시각이 수정한 `server.py`의 수정 시각보다 늦은지 여부

## 결과와 trade-off

- 클라이언트의 다중 필드 정렬 방식과 무관하게 질문 순서가 결정적이다.
- 각 문제 유형 화면은 `Field 1/1`로 표시되며, 하나의 `Field 1/3` form보다 승인
  왕복 횟수가 늘어난다. 순서와 조건부 학습자 정보 동작을 보장하기 위해 이 비용을
  수용한다.
- 이 결정은 [0009 요청 workspace 경로와 서버 주도 사용자 선택](../tracking/decisions/0009-request-context-and-elicitation.md)의 Elicitation 원칙을 구체화한다.
